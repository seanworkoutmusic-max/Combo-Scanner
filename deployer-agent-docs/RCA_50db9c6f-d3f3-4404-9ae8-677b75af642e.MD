# RCA — TD Scanner board empty in production (`/api/scanner/board`)

## Symptom
Published app's Triple-Double Scanner shows nothing / never loads. Preview returns ~8 rows in 10–40s.

## What I verified (prod, run 50db9c6f-d3f3-4404-9ae8-677b75af642e)

1. **Latest code IS deployed.** Prod logs show `GET /api/scanner/board?td_pts=10 → 200`, `GET /api/bets → 200`, `GET /api/live-tracker → 200`. All the recently-added endpoints exist and respond.

2. **The endpoint is NOT 5xx'ing or timing out.** Live probe of `https://combo-edge-scanner.emergent.host/api/scanner/board?td_pts=10` returned **HTTP 200 in 9.8s** with body:
   `{"players":[], "games":10, "books":{"enabled":true,"credits_left":"19","sgp":true}, ...}`
   → `games:10` means the (unauthenticated) Kalshi public markets + Odds API schedule worked. The problem is `players` is **empty**.

3. **Root cause: production `KALSHI_PRIVATE_KEY` does not match the working preview value.**
   `list_secrets` (equals-compare against the preview `backend/.env`) returned:
   - `KALSHI_API_KEY_ID` → matches_expected: **true**
   - `KALSHI_PRIVATE_KEY` → matches_expected: **FALSE**
   - `ODDS_API_KEY` → matches_expected: true
   - `ODDSBLAZE_API_KEY` → matches_expected: true
   The key ID is identical but the private key differs, so RSA/Ed25519 signatures generated in prod will not verify against the public key registered for that key ID → Kalshi rejects auth (401).

## Why a bad Kalshi key empties the whole board (code path in `backend/server.py`)
`scanner_board` builds `players` only from combos that pass the FINAL gate:
```
players = [... for g,p,c,odds,s in todo if (c.get("live") or {}).get("yes_price")]
```
`c["live"]` is set by `_quote(c)` → `kalshi_auth.live_combo_quote(...)` (an authenticated, RSA/Ed25519-signed Kalshi RFQ). When auth fails, `kalshi_auth._call` raises `KalshiAuthError("Kalshi rejected the API key (401)...")`, `_quote` swallows it into `c["error"]`, and `c["live"]` is never set → **every player is filtered out → `players: []`.**
Confirming evidence: `POST /api/props/kalshi-quote → 424 Failed Dependency` in prod logs — that endpoint returns 424 exactly on `KalshiAuthError`/`httpx.HTTPError` from the same signed Kalshi path.

I also confirmed the preview key value is a valid Ed25519 PKCS8 key that `cryptography.load_pem_private_key` parses successfully (even in its single-line form), so the preview key is good and the format `.replace("\\n","\n")` handling is not the problem — the prod value is simply a different/stale key.

## Secondary observations (NOT the root cause)
- `OddsBlaze fanduel NBA unavailable: 404` repeatedly. `ODDSBLAZE_API_KEY` matches preview, so this is most likely "no live NBA data for that book right now," not an auth problem. Even with OddsBlaze empty, combos still reach the Kalshi quote stage via the Odds-API triple-double path (`credits_left:19`, Odds API healthy) — so the Kalshi gate is still the decisive failure.
- **Ingress/proxy timeout:** not the cause of the current symptom — the 200 came back in 9.8s, well inside any timeout. Note for later: when the board DOES have data, the Kalshi RFQ polling (`wait≈6s` per combo) can push the request to 30–60s through the Cloudflare worker proxy; if that ever exceeds the proxy limit it would present as "never loads." Re-evaluate only after the Kalshi key is fixed and rows actually return.

## Fix
**User:** In Deployment Panel → Secrets, set `KALSHI_PRIVATE_KEY` to the same private key that works in preview (leave `KALSHI_API_KEY_ID` as-is — it already matches), then redeploy. After redeploy, re-test `/api/scanner/board?td_pts=10`; it should return populated `players` as in preview.
