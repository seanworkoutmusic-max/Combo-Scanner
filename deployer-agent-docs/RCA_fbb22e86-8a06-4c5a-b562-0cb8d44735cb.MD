# RCA — Deployment Blocked (combo-edge-scanner)

## Symptom
Redeploy request did not complete. The committed deploy run's `trigger_indie` step returned:

```
status 409: {"code":"deployment_blocked","error":"This deployment was blocked. If you believe this is a mistake, please contact support."}
```

## Root Cause
The deployment is blocked server-side by Emergent's abuse/phishing classification — NOT a build, manifest, code, secret, or infra failure.

Evidence:
- Prior redeploy run `fbb22e86-8a06-4c5a-b562-0cb8d44735cb` terminated at the `await_phishing` step:
  `deployer-v3 ... AwaitPhishingClassification ... deployment blocked: there has been an error with this deployment. Please fork the session and start a new deployment (type: wrapError): deployment blocked`
- All downstream steps (`mongodb_migrate`, `manage_secrets`, `deploy`, `health_check`) report `not run: an earlier deploy step failed` — confirming the pipeline was halted upstream, before any build/deploy work.
- The new trigger returns the same `409 deployment_blocked` at the trigger boundary.

## Why this cannot be auto-fixed
The block is enforced at the deploy trigger / Trust & Safety layer. No manifest edit, source fix, secret change, or `resume_pipeline` retry can clear it — a retry returns the identical 409. I did not call `resume_pipeline` because it is guaranteed to re-hit the block.

## Required Action (User / Platform)
- The deployment classification block must be reviewed and lifted by Emergent support.
- The user should contact Emergent support quoting deployment_id `c17901c6-ff77-48eb-b563-ac97c53e37e4` and job_id `e0792315-450a-409e-a54a-20043c794d00`, and/or fork the session to start a new deployment as the block message advises.

Note: The currently LIVE app (active run `f6e66b52-8007-4d2a-92e3-f521cb16584a`, https://combo-edge-scanner.emergent.host) is unaffected — this block only prevents the NEW redeploy from going out.
