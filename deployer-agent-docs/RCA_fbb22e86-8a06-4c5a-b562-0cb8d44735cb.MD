## Symptom

```
status 409: {"code":"deployment_blocked","error":"This deployment was blocked. If you believe this is a mistake, please contact support."}
```

## Root cause (confirmed)
This is a platform trust-&-safety / phishing-classification **block**, applied before any deploy step executes — NOT a code, manifest, secret, tier, or infra fault.

Evidence:
- The immediately prior redeploy run `fbb22e86` failed at the `await_phishing` step (AwaitPhishingClassification):
  `deployment blocked: there has been an error with this deployment. Please fork the session and start a new deployment: deployment blocked`
- `get_step_status` for that run shows every subsequent step (mongodb_migrate, manage_secrets, deploy, health_check) as `not run: an earlier deploy step failed` — confirming nothing in the build/deploy path was reached.
- The new trigger returns HTTP 409 `deployment_blocked`, marked `retryable:false`.

## Why no fix was applied
- The block is server-side and non-retryable. Re-firing `resume_pipeline` will deterministically return the same 409.
- There is no deployer-agent tool to lift a trust-&-safety block. It is not manifest-, source-, or secret-related.

## Impact
- The currently live app (run dde6cebf) is unaffected and still serving. This block only prevents the NEW redeploy from going live.

## Required action
1. Contact Emergent support to review/clear the deployment block, quoting deployment_id c17901c6-ff77-48eb-b563-ac97c53e37e4, job_id e0792315-450a-409e-a54a-20043c794d00, and run_id fbb22e86-8a06-4c5a-b562-0cb8d44735cb.
