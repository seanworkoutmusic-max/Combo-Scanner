# RCA — Deployment blocked (trust & safety / phishing classification)

## Symptom
The committed deploy run could not start. The `trigger_indie` step returned:

```
status 409: {"code":"deployment_blocked","error":"This deployment was blocked. If you believe this is a mistake, please contact support."}
(type: deployer_indie_4xx, retryable: false)
```

## Root cause
This deployment (`combo-edge-scanner`, deployment_id `c17901c6-ff77-48eb-b563-ac97c53e37e4`) has been flagged and blocked server-side by the platform's abuse/phishing classification. This is confirmed by the immediately prior redeploy run `fbb22e86-8a06-4c5a-b562-0cb8d44735cb`, which failed at the `await_phishing` step:

```
await_phishing: activity error (... AwaitPhishingClassification ...):
deployment blocked: there has been an error with this deployment.
Please fork the session and start a new deployment : deployment blocked
```

Once a deployment is in this blocked state, every new trigger is rejected at the gate with a non-retryable HTTP 409 `deployment_blocked` before any pipeline step (build/deploy) can run.

## Why this is not auto-fixable
- The 409 is returned by the deployment gate, before build/manifest/source steps execute, so no manifest edit or code change can clear it.
- `retryable: false` — re-firing `resume_pipeline` will return the same 409.
- It is a trust-&-safety classification decision, which only the Emergent platform/support side can review and lift.

## Current live state (unaffected)
The currently active run `f6e66b52-8007-4d2a-92e3-f521cb16584a` (secret_reuse, success) is still serving at https://combo-edge-scanner.emergent.host. The block prevents a NEW version from going out; it did not take the existing live app down.

## Required action
1. The user must contact Emergent support to review/appeal the block (quote deployment_id `c17901c6-ff77-48eb-b563-ac97c53e37e4` and job_id `e0792315-450a-409e-a54a-20043c794d00`). The 409 message itself directs: "If you believe this is a mistake, please contact support."
2. Per the pipeline message, the user may also need to fork the session and start a new deployment once the block is cleared.

No deployer-side retry will succeed until the block is lifted.
